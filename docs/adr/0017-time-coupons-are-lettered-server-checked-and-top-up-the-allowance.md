# Time Coupons are lettered, server-checked, and top up the Allowance

A [[Time Coupon]] is a gift of time made ahead of the moment: minted in batches on the server, printed or copied, handed to the kid, spent whenever the kid chooses. It is six letters followed by the minutes in three digits — `KRTVXM030`, shown as `KRT-VXM-030` — where an [[Extra Time Code]] is nine digits. The letters come from a fixed 19-letter alphabet with no vowels and no `I`, `L`, `O`. Redeeming one asks the server, which marks the coupon used and answers with the minutes; those minutes are added to today's [[Allowance]] on that Client.

Three decisions travel together here, and each one exists because a coupon is a *standing promise* where an Extra Time Code is *live parental intent*. The system already treats that distinction as load-bearing — it is why only a [[Grant]] beats [[Downtime]] — and a coupon sits on the standing side of it in every respect.

**Letters, not digits.** A coupon stored in a database and a code derived from the [[Grant Seed]] cannot share an alphabet without one of two failures: a coupon that accidentally matches that minute's live code, or a verification order (seed first? database first?) that silently becomes load-bearing. Letters dissolve both — the Client knows *at parse time* which kind of code it holds, a kid can see which kind they were handed, and an un-updated Client rejects a coupon cleanly instead of misreading it. No vowels means six random letters can never spell a word on a slip handed to a child; no `I`/`L`/`O` means no glyph reads two ways, which is the same failure ADR-0014's grouping exists to catch. The trailing three digits stay digits: the minutes travel in the clear in both code families, one convention.

**Server-checked, online-only.** The coupon inventory lives on the server and nowhere else, so redemption is the system's first code path that requires the server to answer. That runs against a principle several ADRs defend hard — the block screen appears exactly when the server is least likely to be reachable — and it is accepted deliberately, because the offline guarantee protects *emergencies*, and a coupon is never one. The bedtime paths all still work offline: exit via [[Admin Code]], an Extra Time Code from a [[Trusted Device]]. A coupon that cannot be checked right now is still good, and the Client says exactly that — "try again later" is the one refusal that invites retry.

**Allowance top-up, not a Grant.** A standing promise carries no live parental intent, so a coupon must not beat Downtime — and "beats an exhausted Allowance but not Downtime" is already, word for word, how Allowance behaves. Redemption therefore adds the minutes to today's Allowance: they pause on lock, Downtime keeps beating them, and what is unspent dies at local midnight. The precedence order `Grant > Downtime > Allowance` gains no fourth tier, and `EnforcementEngine` gains no capped-window state. Redeeming during Downtime is refused on the Client before the server is ever asked, so the coupon stays unspent rather than buying minutes the kid cannot reach before midnight kills them.

## Considered options

- **Sync the coupon inventory (even hashed) to every Client, for offline redemption.** Rejected: it distributes the coupons to the very machines they will be spent on, demands a sync-and-invalidation protocol, and turns revocation into a race against an offline redemption. The whole point of revoke-is-delete is that the server's answer is the only answer.
- **Digit-only coupons, distinguished by checking the database first.** Rejected: collisions with live codes become possible, lookup order becomes semantics, and neither the kid nor an un-updated Client can tell the two kinds apart. Format is the honest discriminator.
- **A Grant-style wall-clock window, capped at Downtime.** Rejected: a 30-minute coupon redeemed ten minutes before Downtime would silently burn to ten and be marked used — a gift with a gotcha in it. Under the Allowance model a coupon is always worth its printed minutes of unlocked screen.
- **Reactivating used coupons.** Rejected: it breaks "used means used", and leaves the timeline saying *redeemed* while the list says *fresh*. The case it would serve is served by minting a replacement, which batch minting makes a two-click act.

## Consequences

- Redemption becomes a client→server exchange (PROTOCOL.md gains a request/response pair), and refusals are honest and specific: already used, expired, wrong machine, not valid (unknown and revoked are indistinguishable by design), not during Downtime, and server unreachable — only the last invites trying again.
- One entry box serves both code families; the Client dispatches on shape. Entry is case-insensitive and the canonical form is uppercase — the Client uppercases before sending, the server before lookup. ADR-0014's rules carry over unchanged: separators stripped on entry, grouping shown but never stored, the copy button puts bare characters on the clipboard so a coupon pasted from a messaging app just works.
- Revoke is hard delete. The coupon list is inventory, not audit: a redemption outlives any deletion as an Event on the Client's timeline, which is where this system keeps its evidence.
- Expiry is optional, runs through the named date inclusive, and turns at *server-local* midnight — the coupon is a server-side object, and a Global coupon has no single Client whose midnight could apply. Everything else in the system keeps turning at Client-local midnight.
- A Client that predates this feature rejects letters at parse and can redeem nothing until it updates — which it does within minutes of connecting, and connectivity is a precondition of redemption anyway.
